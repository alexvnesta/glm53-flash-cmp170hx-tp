# Direct FP32 accumulation in the routed gate/up kernel

Outcome: **retain the qualified row32 production build**. Direct FP32
accumulation passes the bounded numerical/functional checks but does not
improve concurrent token throughput.

This experiment targets periodic accumulator folding in the largest individual
kernel in the production trace: the SM80, 3-bit/mul1 wide routed gate/up path.
The existing kernel accumulates in FP16, then periodically converts and adds
its partials into FP32 at a four-slice cadence. The candidate keeps FP16 inputs
and accumulates directly in FP32 Tensor Core registers, removing that explicit
conversion/add/reset loop.

It reuses ExLlamaV3's existing
[`ptx_mma_m16n8k16` FP32 helper](https://github.com/turboderp-org/exllamav3/blob/0f685aa9fda3a98a864149b367b7ef570257572e/exllamav3/exllamav3_ext/ptx.cuh),
which implements NVIDIA's documented
[FP16-input/FP32-accumulator instruction](https://docs.nvidia.com/cuda/parallel-thread-execution/#matrix-fragments-for-mma-m16n8k16-with-floating-point-type).
The input-fragment mapping and zero upper eight rows are preserved. The two
lower-row FP32 output elements feed the existing shared reduction.

The production warp layout, register-prefetch depth, decoder, expert routing,
activations, down kernel, 32-row native capacity, two active request slots and
TP communication policy are retained. The altered accumulation applies only
to SM80, integer 3-bit, mul1, wide gate/up calls. Other codebooks, widths,
architectures and down calls retain the original arithmetic. The rounding
path changes, so this is not a bit-equivalence claim.

The hypothesis is that removing periodic folding reduces instruction work
while preserving block residency and useful warp parallelism. The preceding
[warp-layout experiment](MOE_RETILE_2026-10-16.md) lowered register use but also
lowered eligible-warp and issue rates. This candidate preserves that layout.

## Qualification contract

The existing `sustained.py`, `measure.py` and `code_oracle.py` remain unchanged.
They submit the same 24 structured/code tasks, temperature zero, 768-token
budgets, low/high effort separately, and one/two/four agents with immediate
backfill. Four agents share two active request slots. Each profile receives
identical eight-request low/high warmups. High-effort two/four-agent cells
repeat twice per profile.

Aggregate tok/s counts actual API completion tokens including reasoning over
the full workload wall time. Each agent's actual tokens use the same wall
time; they sum to the aggregate before rounding. Validation, prefill and
queueing remain included. Output lengths, errors and failed scores are kept.
No prompt, budget, oracle or failed answer is repaired during comparison.

Promotion requires at least 2% higher pooled high-effort throughput at both
two and four agents, no low-effort concurrent regression, and serial rates
within 2%. Numerical, JSON and lifecycle checks must pass before a candidate
can proceed to a guarded production canary, soak and cache-restart recovery.
The standard and full-width dense-reference tolerances are unchanged.

## Source and build custody

`prepare_routed_moe.py --mode fp32` verifies the entire qualified source tree
before creating an isolated destination. It preserves the original header,
adds a derived header included only by the K3 compilation unit, and fails
closed if any arithmetic anchor changes. Reproducing preparation yields an
identical 973-file manifest. The original serving defaults are unchanged.

The CPU-only incremental build hides GPUs, rebuilds one CUDA object and reuses
190 byte-attested objects. It took 21.80 seconds and imported the row32 native
extension without initializing CUDA. Its native SHA is
`61ac5bb8d31bd5883cf6b0e3331292dd6b9243955f95fc706a547f9d34708259`.
The derived-header SHA is
`15a5e6da06d82f19b2d8457674d93309a93e46dcfa9ef01895d8f69daf48c24d`.
Static compilation reports 64 registers/thread for both control and candidate,
preserving the two-block register-residency limit. Dynamic occupancy and
end-to-end throughput require the GPU measurements below.

The exclusive controller checks three idle snapshots, exact serving identity,
sole-unit GPU ownership, inactive Qwen and low host CPU pressure before taking
the GPUs. It restores qualified production on every exit. Read-only CPU/GPU
telemetry is collected through the comparison; other clients and CPU jobs are
left running.

## Numerical and hardware screen

Both binaries pass the 34-case standard GPU oracle and 22 full-width routed
cases, with the original dense-reference tolerance and repeated-output bit
checks. The full-width cases cover both GPUs and rows
1/2/4/7/8/9/16/17/24/31/32, including foreign expert masking, empty rows,
FP32 gate/up scratch and activation clipping. Four of 22 output hashes match
across binaries; the others differ while passing the unchanged reference.
These are bounded random-projection checks, not universal model equivalence.

The isolated Nsight Compute capture uses 32 rows, GLM projection widths,
146 local experts from 288, and 127 selected local slots on GPU0. Clock and
cache controls are disabled. It runs separately from unprofiled serving.

| Metric | Control | Direct FP32 |
|---|---:|---:|
| Registers/thread | 64 | 64 |
| Register-limited resident blocks | 2 | 2 |
| Active-warp occupancy | 49.56% | 49.57% |
| Instruction issue active | 77.98% | 73.48% |
| Eligible warps/active cycle | 2.61 | 2.37 |
| DRAM throughput/peak | 17.12% | 17.11% |
| Captured A-kernel duration | 1.7472 ms | 1.7486 ms |

Removing the explicit folding loop did not improve this captured duration.
Lower issue activity alone does not establish a faster kernel. No server token
rate is inferred from the hardware capture or whole-operation CUDA timings.

The static hot-function SASS count also changes: `HADD2` falls from 250 to 218
and `FADD` from 340 to 308, while both contain 24 `HMMA` instructions. These
are static instruction counts across the compiled function, not dynamic loop
counts or recovered cycles. They support that compilation removed work, but
the hardware duration still needs to improve before that is a speed benefit.

The two-agent low-effort candidate finishes about 5.1% sooner while emitting
about 7.7% fewer tokens. Five of its six `array-100` answers use compact JSON
without spaces after commas: **198 tokens** instead of
**293 tokens**. Both return the same correct 96 integers. The baseline has 95
comma-space pairs; those compact candidate answers have none. This explains
most of the token-count difference in that cell.

This is an observed output-format effect alongside the changed numerical path,
not evidence that its kernel computes tokens faster. Other cells also have
different answer lengths. The payload, effort, budgets and validators remain
frozen; the actual answers and scores are retained. No format normalization
or prompt change is used to manufacture a matched token count.

## Checks and production disposition

The candidate passes nine exact JSON-object cases, a mixed-filter
wave, cancellation with survivor and replacement-slot reuse, and three
high-effort coding pairs. CPU checks pass 39 tests on Linux; macOS passes
38 with one platform skip. HTTP checks pass 44 tests and response-lifetime AST
checks pass four. The pinned engine source is reproduced before HTTP checks.

Host CPU pressure remained low during scored traffic. Measured CPU-PSI
10-second averages are recorded per arm in the receipts; no host-load timing
exclusions are needed in this comparison. Other clients/jobs were left running.

Control CPU-PSI avg10 samples: mean 0.104%, maximum 0.53%.
FP32 CPU-PSI avg10 samples: mean 0.104%, maximum 1.15%.

Independent production inspection at `2026-10-16T20:29:39.643671+00:00` verifies the
full source manifest, native binary, sole-unit GPU ownership, healthy idle
state, empty requests/queue/leases, Weightless alpha 2 on both devices,
`NRestarts=0` and inactive Qwen. Qualified production retains native SHA
`f0a25e2c707748eed0679d7e58f92907ebd6eea4e3b2b1605037382baeb2d046` and profile digest
`2bfd7ca630f488034cfc1be093317719aeb41e227a8e8766a3e2c856e637c91c`.

**Do not promote the FP32 candidate for throughput.** It preserves occupancy
and removes explicit folding work, but misses the predeclared serving-speed
gate. No new candidate canary, soak or cache-restart qualification is claimed.
The default launcher, production service and communication policy retain the
qualified row32 build. All experiment serving/controller/monitor units exit.
